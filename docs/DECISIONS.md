# 决策记录

初始日期：2026-10-21。以下保留文档阶段的决策及理由；当前采用情况结合任务与后续验收记录核实，不将初始“待验证”文字当作最新项目进度。
“基线”表示可据此开工；“待验证”不能写成已实现。产品细节以 PRODUCT 为准。

## D-001：使用 C# / .NET 10 LTS / WPF

- 状态：已采用。原起步状态为“基线，待 P0 原型验证”；2026-10-22 阶段 0 单屏范围已验收，见 [P0-005 复核 R2](reviews/P0-005-review.md)。多屏等未验证边界仍保留，不改变下述调整条件。
- 原因：项目只针对 Windows，重点是透明窗口、托盘与 Win32 桌面集成；C# 便于拆出可测试的行为核心。
- 选择 .NET 10 而不是本机已有的 .NET 7 Runtime：需要仍受支持的开发基线，旧 Runtime 也不能替代 SDK。
- 代价：透明窗口性能、非激活输入和混合 DPI 需要实测；非跨平台路线。
- 调整条件：提供可复现的输入/性能问题与局部替代实验，再决定更换渲染或窗口实现。
- 来源：[.NET 支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)、[WPF 窗口](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/windows/)。

## D-002：两项目、单进程、每宠一个紧凑窗口

- 状态：基线。
- 原因：Core 隔离业务与系统；App 统一输入、窗口和存档；双宠同进程易于共享会话和每日额度。
- 代价：需要处理跨窗口坐标与命中；不能靠全屏透明层掩盖输入问题。
- 调整条件：实际宠物数量或测量数据证明窗口模型不合适时再评估共享渲染层。

## D-003：本地规则与 JSON 起步

- 状态：基线。
- 原因：用户期望的情绪、社交、随机事件可用规则表达，无需持续模型调用；数据量初期较小。
- 代价：需要调参数与动画，不能把规则或频次包装成智能预测；JSON 仍要做版本与恢复。
- 调整条件：实际数据量和查询需求需要数据库，或用户明确增加 AI 对话等功能。

## D-004：统一运动写入与可中断行为

- 状态：基线。
- 原因：用户操作、物理、社交和窗口跟随会竞争位置；先有所有权规则再叠加功能。
- 实现含义：所有模块提交请求，运动协调器生成最终状态；动画只负责表现。
- 代价：比给每个动作直接写窗口坐标多一层，但可测试和交接。

## D-005：先单宠体验，再双宠，再窗口与习惯能力

- 状态：基线；用户可改变优先级。
- 原因：先验证透明输入、物理和行为中断，避免系统集成失败拖累全部功能。
- 保留：双宠是核心长期目标；强制休息和图标定位没有被删除，初版先缩小实现边界。
- 调整条件：用户明确把某功能提升为首个交付目标，更新 PRODUCT/TASKS，不只改聊天计划。

## D-006：采用 MSTest 验证核心，实机验证桌面

- 状态：基线。
- 原因：统一 .NET 工具链，可替换时间与随机源验证规则；原生输入兼容性不能靠纯单测证明。
- 代价：需要保留人工验证记录；没有桌面条件时部分任务只能等待验证。
- 来源：[MSTest 入门](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-csharp-with-mstest)。

## D-009：取消快速移鼠受惊功能

- 日期：2026-10-25。状态：用户明确决定，已取代R-01原快划/甩动需求。
- 授权原文：“‘快速移动鼠标时小熊受惊’这个功能完全移除，太鸡肋了，你可以改产品代码，改好了告诉我怎么和开发AI说”。
- 决定：删除自动甩动检测、专用速度/距离采样、阈值和冷却、dodge注册及相关专用测试；悬停直接使用当前鼠标位置，不保留默认关闭开关或后续待办。
- 保留：悬停好奇、抚摸、身体拖动、委屈表达与存档；受惊PNG仍供拖动临时脸使用。阶段2的拖动抛掷速度估算是另一需求，不受本决定取消。
- 历史边界：旧审查、整改、运行证据和设定图保留并按对应版本解释；其中“快划待验证”不再是当前任务门槛。不得因读到旧报告而恢复已取消功能，也不以别名重新接回鼠标速度触发。
- 调整条件：仅在用户再次明确提出时重新讨论，不由开发AI自行恢复。实现与验证见 [移除交接](handoffs/INPUT-001-remove-mouse-fright.md)。

## D-010：头部和双耳允许拖动并保留抚摸

> D-013后头部微移仍保留但不计分；本条的拖动分流/捕获规则继续有效，亲近度部分失效。

- 日期：2026-10-25。状态：用户报告缺陷并授权修正。
- 来源：“熊两眼连线上方所有区域都没有纳入点击和拖动的判定范围，请你修正”。
- 决定：所有可见部位均可作为拖动起点，取消旧R-02“拖动应从身体区域开始”的限制；头部小幅移动仍保留抚摸，明确的拖动接续原捕获和最初抓取点，不误计亲近度。
- 原因：头部原本进入抚摸候选，转拖动时丢捕获、重建偏移且只看相邻事件距离，造成头顶/双耳快拖、慢拖均不可靠。采用从按下点累计的8DIP容差并保留单次阈值，移出头部时接续拖动；透明起点仍拒绝，不扩大为全窗口命中。
- 边界：不取消抚摸，不恢复D-009已删除的快速移鼠受惊，不新增纯点击表情或身体动作。旧审查/证据按原版本保留；当前验收见INPUT-002交接。

## D-011：安静柔软的自然观感首版

- 日期：2026-10-25。状态：用户批准首版实施，原文“很好，这部分按你说的做”，对应用户粘贴的自然观感方案。
- 决定：先统一待机底图，眨眼只改眼睛；添加半闭/闭合过渡、3～7秒间隔、约220ms开闭及低概率双眨。好奇约2秒后自动平静，提前离开0.3秒退出，重新触发仍需离开0.5秒和完整驻留1.2秒。
- 取舍：变化少、有原因且能恢复平静；不靠整身图片交叉淡化，避免重影。普通眨眼与舒服情绪分开。原INPUT-003的0.5秒退出是历史版本，现由本决定细化；其缺陷修复结论不改写。
- 边界：身体动作、眼球追踪、拖动专用脸与松手过渡、抚摸成功笑脸、委屈素材统一仍待后续安排；不自动推进P1-004，不把作者自测当独立美术验收。

## D-012：接受自然观感首版，保存基线后完善拖动反馈

- 日期：2026-10-25。来源：助手建议确认现版观感、核对并提交/按授权推送、下一步温和拖动表情与松手过渡；用户回复“我觉得现在很不错，按你说的做”。
- 决定：接受ART-002当前整体观感；核对截至ART-002的叠加变更后，本次提交并普通推送至既有origin/main；随后执行ART-003。该授权不推导今后每轮自动推送，不伪造独立监理结论。
- ART-003边界：拖动由瞪眼受惊改为轻微意外；松手约250ms面部过渡回待机，位置与鼠标捕获立即结束，不延迟松手、不改抓取点；新输入可打断，暂停冻结。仍使用固定身体底图，不做全身透明交叉淡化或身体动作。
- 抚摸成功舒服表情、其他委屈优化及P1-004继续待安排。提交前保留既有P1-004撤回，不能把旧提交标题当作当前已实现范围。

## D-013：完全移除好感度系统

- 日期：2026-10-26。来源：用户明确要求“把好感度系统完全移除，我不需要这个系统，从文档到代码做全面整改”。
- 决定：删除亲近度数值、抚摸计分和计分冷却、亲近度衰减、运行时及存档字段；取消D-008延后的高亲近主动靠近计划。不是暂缓，不留开关、占位字段或以后自动恢复的待办。
- 保留：委屈记忆是独立机制；头部小幅手势不计分，超过8DIP或移出头部接续拖动，原抓取点/捕获保持。悬停、自然眨眼、小熊素材、温和拖动/松手表情不因本决定撤回。
- 兼容：state继续为v2；旧JSON的已移除字段作为未知字段忽略，正常保存不再写入，不清空其他状态；v1默认值及未知高版本只读保护保留。不直接改写用户真实存档。
- 历史：D-008被本决定替代；D-010的抚摸计分部分被本决定替代，头部拖动规则保留。旧审查/整改/交接/实机证据反映当时版本，不删改旧结果，也不据此恢复取消需求。实现与本轮验证见[移除交接](handoffs/EMOTION-001-remove-affinity.md)。
