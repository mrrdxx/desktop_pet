# 决策记录

初始日期：2026-10-21。以下保留文档阶段的决策及理由；当前采用情况结合任务与后续验收记录核实，不将初始“待验证”文字当作最新项目进度。
“基线”表示可据此开工；“待验证”不能写成已实现。产品细节以 PRODUCT 为准。

## D-001：使用 C# / .NET 10 LTS / WPF

- 状态：已采用。原起步状态为“基线，待 P0 原型验证”；2026-10-22 阶段 0 单屏范围已验收，见 [P0-005 复核 R2](reviews/P0-005-review.md)。多屏等未验证边界仍保留，不改变下述调整条件。
- 原因：项目只针对 Windows，重点是透明窗口、托盘与 Win32 桌面集成；C# 便于拆出可测试的行为核心。
- 选择 .NET 10 而不是本机已有的 .NET 7 Runtime：需要仍受支持的开发基线，旧 Runtime 也不能替代 SDK。
- 代价：透明窗口性能、非激活输入和混合 DPI 需要实测；非跨平台路线。
- 调整条件：提供可复现的输入/性能问题与局部替代实验，再决定更换渲染或窗口实现。
- 来源：[.NET 支持政策](https://dotnet.microsoft.com/en-us/platform/support/policy)、[WPF 窗口](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/windows/)。

## D-002：两项目、单进程、每宠一个紧凑窗口

- 状态：基线。
- 原因：Core 隔离业务与系统；App 统一输入、窗口和存档；双宠同进程易于共享会话和每日额度。
- 代价：需要处理跨窗口坐标与命中；不能靠全屏透明层掩盖输入问题。
- 调整条件：实际宠物数量或测量数据证明窗口模型不合适时再评估共享渲染层。

## D-003：本地规则与 JSON 起步

- 状态：基线。
- 原因：用户期望的情绪、社交、随机事件可用规则表达，无需持续模型调用；数据量初期较小。
- 代价：需要调参数与动画，不能把规则或频次包装成智能预测；JSON 仍要做版本与恢复。
- 调整条件：实际数据量和查询需求需要数据库，或用户明确增加 AI 对话等功能。

## D-004：统一运动写入与可中断行为

- 状态：基线。
- 原因：用户操作、物理、社交和窗口跟随会竞争位置；先有所有权规则再叠加功能。
- 实现含义：所有模块提交请求，运动协调器生成最终状态；动画只负责表现。
- 代价：比给每个动作直接写窗口坐标多一层，但可测试和交接。

## D-005：先单宠体验，再双宠，再窗口与习惯能力

- 状态：基线；用户可改变优先级。
- 原因：先验证透明输入、物理和行为中断，避免系统集成失败拖累全部功能。
- 保留：双宠是核心长期目标；强制休息和图标定位没有被删除，初版先缩小实现边界。
- 调整条件：用户明确把某功能提升为首个交付目标，更新 PRODUCT/TASKS，不只改聊天计划。

## D-006：采用 MSTest 验证核心，实机验证桌面

- 状态：基线。
- 原因：统一 .NET 工具链，可替换时间与随机源验证规则；原生输入兼容性不能靠纯单测证明。
- 代价：需要保留人工验证记录；没有桌面条件时部分任务只能等待验证。
- 来源：[MSTest 入门](https://learn.microsoft.com/en-us/dotnet/core/testing/unit-testing-csharp-with-mstest)。

## D-007：P0-002 带 Alt+Tab 已知限制结束验收

- 日期：2026-10-21。状态：用户接受的本次验收例外，不代表修复或测试通过。
- 依据：用户在监理对话直接确认七项中六项通过、Alt+Tab 拖动切换仍跟随但无需本轮修改；授权原文、范围及证据统一维护在 [监理报告 R2 的 KL-001](reviews/P0-002-review.md)。
- 决定：允许 P0-002 完成并进入 P0-003，不以低优先级的已接受限制阻塞后续工作。
- 边界：不豁免正常松手、菜单恢复等其他行为。保留原测试预期，后续要求变化或新功能依赖时再评估，不自动安排本轮修复。
