# 审查、整改与复核规则

本文件是审查协作流程的权威出处。适用于已有或后续明确发起的监理审查，不要求每个小任务都新增审批流程。
这是协作约定，不是操作系统权限隔离；当前所有可写仓库的 agent 技术上仍能编辑文件。
用户明确指示优先；例外必须记录授权来源，不能从“继续”“同步文档”等普通指令推断可改审查结论。

## 1. 职责与文件归属

- **监理**：本监理对话，或用户明确指定的其他审查者。维护 `docs/reviews/` 中的报告、复核结果及对应证据。
- **开发 AI**：实现修复；维护 `docs/remediation/` 中的整改说明和开发自测证据；按正常职责更新产品、架构、任务与状态文档。
- **用户**：提供真实体验反馈，决定需求与优先级；可以明确接受风险、豁免阻断或指定新的监理。
- 自测者不能自行扮演监理签发复核通过。更换 agent 或上下文不会自动改变职责。
- 开发 AI 不得改写、删除、重命名、搬移或用其他文件替换监理报告及复核证据；此限制包括标题、原问题、严重程度、状态和结论。批量格式化也不得覆盖这些文件。
- 发现报告错误、笔误、链接失效或代码行号过时，在整改记录提出，由监理修正；不得借“文档同步”消除问题。
- 监理更正自己的报告时保留原始问题及必要上下文，在修订/复核节注明日期、变化与理由；严重程度调整、问题撤回也要留下原因。
- 用户明确要求其他角色编辑报告时，只执行所授权范围，注明来源；不能伪装成原作者的复核意见。

## 2. 唯一出处与引用

- 报告：`docs/reviews/<任务ID>-review.md`；同任务多轮需要独立报告时加稳定后缀。
- 整改：`docs/remediation/<对应报告文件名去掉-review>-response.md`；每份报告对应一份主整改记录，后续轮次追加。
- 模板：[整改记录模板](templates/REMEDIATION_TEMPLATE.md)。
- 问题身份是“完整报告路径＋F-xx”，不同报告的 F-01 不能混用；已发布的编号不重排、不复用。
- 问题事实、阻断范围及监理结论只在报告维护；开发措施和自测证据只在整改记录维护。其他文件链接引用。
- STATUS 保存当前摘要、审查/整改入口、待谁处理及下一步；TASKS 仍是任务状态唯一出处。
- 已关闭记录保留在原路径。不为缩短 STATUS 删除证据或归档仍未关闭的问题。
- 工具内部 task.md、记忆文件、聊天总结不替代上述记录，不具备监理签字效力。

## 3. 发起审查与阻断范围

监理在报告写明任务、日期、审查对象版本、方法、限制、问题 ID、影响、整改目标和可观察验证条件。
有 Git 时记录 commit 并说明未提交修改；无 Git 时记录相关路径、时间，必要时用文件摘要标识版本，不捏造 SHA。
旧报告缺少版本标识时明确记录证据限制，下一次复核补齐，不反推或伪造历史版本。

报告必须明确哪些问题阻断哪个任务/阶段；严重程度不自动等于门槛。建议项不能无声升级成全项目停工条件。
已有报告有歧义时，开发 AI 记录问题并请求澄清，不自行解释为已放行；可继续当前范围内不受影响的工作。
P0-002 的原阻断范围及后续解除依据见 [审查报告](reviews/P0-002-review.md) 的最新复核；流程文件不另行维护动态问题状态。

## 4. 开发整改流程

1. 阅读报告和当前权威规格，确认每个问题的影响与验收目标。
2. 正在修改时，按 TASKS 规则将当前任务设为 in-progress，且最多一个；不要为每个 F 编号建立重复任务状态表。
3. 在独立整改记录逐项写措施、变更文件、版本、验证步骤/命令、实际结果、未验证项；不复制整段报告。
4. 只写实际做过的验证。编译、静态判断、窗口枚举、屏幕观察、实际输入操作分别说明，不能互相替代。
5. 自测完成后标“已整改，待复核”；缺验证能力时标“已修改，待自测/实测”并给操作步骤；有异议时写反证与建议。
6. 同步关联规格和 STATUS 的入口，任务设为 awaiting-verification，向用户提交复核请求。不代改报告状态，不自行签“复核通过”。
7. 等待复核期间不推进依赖未满足的任务；可以完善复现证据、修复同任务其他问题或做不影响验收对象的文档工作。

开发处置措辞只表示开发侧进度：未开始、整改中、已修改待验证、已整改待复核、有异议待裁定。
它不是第二份项目任务状态，也不是监理问题关闭状态。

## 5. 复核、争议与用户决定

- 监理读取整改记录，对照真实代码、版本和证据逐项复核；需要时重跑验证，没有条件时说明限制。
- 复核结果由监理在原报告追加：通过、未通过或部分通过，并指出覆盖范围、证据和剩余条件。
- 部分通过仍是未关闭；仅静态修复通过而要求的人工验证缺失时，不得将整个问题标为通过。
- 监理可以采纳开发方反证、修正原判断或撤回问题，并记录原因；报告不是不容质疑的需求来源。
- 改需求才能解决的争议由用户决定，再更新 PRODUCT/DECISIONS；审查意见不能暗中扩大产品需求。
- 用户可以明确豁免某个问题对指定任务/阶段的阻断。开发 AI 在整改记录保存可追溯授权原文、日期和范围，等待监理核验记录，或由用户直接形成仓库裁决。
- 用户明确放行可按授权范围执行，无需再次索取同一批准；应区分“用户豁免”与“监理复核通过”，不得把前者改写成后者。
- 用户反馈“测试正常”只证明其实际操作覆盖的范围，不自动代表风险豁免或全部监理问题通过。

## 6. 关闭条件与后续变化

有审查阻断项的任务标 done 必须同时具备：正常任务验收证据、同步的文档、阻断项的监理通过/有理由撤回或用户明确豁免依据。
开发 AI 可据已存在的有效依据更新 TASKS，并在 STATUS 链接到对应复核或裁决，不必再请求一次重复确认。

修复经过复核后又发生影响结论的代码/配置/环境变化，旧结论只适用于旧版本。开发 AI 在整改记录标明变化、重新验证并请求复核，不修改旧签字来适配新版本。
确实影响已完成任务验收时，按新证据更新 TASKS，不继续引用失效结论声称当前版本通过。监理在报告追加重新打开/补充复核记录。
没有新变化或风险，不要求反复复核相同证据，也不把一次审查变成无限审批。
