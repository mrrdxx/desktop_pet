# Git 协作与备份纪律

本文件约束版本管理，不替代 TASKS 的任务状态或 REVIEW_PROCESS 的验收规则。
用户指定目标：`https://github.com/mrrdxx/desktop_pet`。远端是否存在、可见性、默认分支和已有历史须实际查询，不凭 URL 推断。

## 1. 授权边界

- 普通“继续开发”“同步文档”不包含 commit/push 授权。默认不自动提交或推送，沿用 AGENTS。
- 用户明确要求“按 Git 纪律开发并在每个已验证小步后本地提交”时，授权范围内可持续本地 commit，不必逐次确认；未授权 push 时仍不得推送。
- 用户明确要求“初始化并首次提交、推送到上述仓库”时，可完成本次操作；不自动推导后续每轮推送授权。用户明确授权持续推送时记录范围并沿用。
- 不自动创建远端仓库、修改公开/私有设置、安装工具、发布 Release 或配置自动部署。
- 认证不足时说明具体缺失，由用户通过官方登录入口完成；不要索要聊天中的 Token，不将凭据写进 URL、文件、日志或 shell 历史。检查本地提交身份，不擅自编造作者或修改全局身份。

## 2. 每轮开始

- 先读 AGENTS、STATUS、当前任务；检查 `git status --short --branch`、必要 diff、当前分支、remote URL 和未推送提交。
- 没有 .git 时如实记录，不把工作区文件摘要说成 commit；初始化必须有明确授权。
- 一个工作目录同时只由一个 agent 执行暂存、提交、合并和同步。监理/开发共用目录时串行交接，分支不能隔离同一目录中的并发修改。
- 不覆盖已有或来源不明的修改；不以“清理工作区”为理由执行 reset/clean/restore。

## 3. 首次接入远端

1. 核对已有 .git、远端地址、登录与本地提交身份；用只读查询检查远端引用/默认分支。认证失败不等于空仓库。
2. 先检查忽略规则、待提交清单和敏感内容。源码、正式资源、测试、构建配置及权威 docs 纳入；排除 bin/obj/artifacts、工具私有记忆、缓存、用户存档和凭据。
3. 空远端：在本地首次初始化时可采用 main，创建当前真实基线，再普通 push 并设置 upstream。不能把 P1-002 标 done 来包装基线。
4. 非空远端：先 fetch 并检查历史。保留本地现有文件和远端内容，选择有记录的整合方法；不可用强推覆盖 README/代码，也不盲目 pull 合并无关历史。存在无法自行判断的内容冲突时提出具体差异，保留两方内容。
5. 推送前核对目标 URL、分支、提交清单、暂存 diff 和证据范围。推送后实际读取远端分支 SHA，与本地目标 commit 比较；未成功就如实记录失败，不重复制造提交。
6. 不改变仓库可见性，不启用 Pages/Actions/Release 等额外能力来完成单纯备份请求。

## 4. 提交范围与频率

- 有本地提交授权时，以可解释、可验证的小步提交；不必每个文件一个提交，也不把整个阶段和无关改动混成一次。
- 代码/测试及直接相关的规格、状态、整改记录一起同步。先检查 diff，再按明确路径暂存，检查 `git diff --cached` 后提交；不未经检查就 `git add .`。
- 监理明确交付的报告/状态变更可以按授权随基线提交；“允许提交已有文件”不等于允许开发 AI 改写报告。提交前识别是谁的修改，不揽作自己实现。
- 提交说明建议 `feat(P1-002): ...`、`fix(P1-002): ...`、`test(P1-002): ...`、`docs: ...`；描述实际内容，不写虚假的“验收全部通过”。
- 已自测但待体验/复核的代码允许提交，TASKS 仍保持真实状态。必要的中途保存提交明确标 WIP 和未验证范围；提交本身不代表验收或里程碑完成。
- Git 初始备份不伪造过去每一步的 commit，也不回溯编造历史测试记录。

## 5. 证据与敏感文件

- .gitignore 是过滤器，不是敏感内容审计；已经跟踪的文件不会因新增 ignore 自动取消跟踪。提交前检查实际文件清单，避免上传本机日志、聊天、Token、用户存档或无关内容。
- `.codefree/`、`.codefree-ide/` 默认作为本机私有状态排除。将来确有团队共享配置时单独审查白名单，不整体解除忽略。
- `docs/reviews/evidence/` 的已保留审查证据应纳入版本控制，不因后缀为 txt/png 被批量排除；存档测试的合成坏数据不要与真实用户存档混淆。
- `artifacts/` 中有早期验证附件和临时探针。首次推送须列明哪些重要依据仅存在于本机，不能宣称历史证据已完整备份，也不能因此取消整个 artifacts 忽略。
- 重要证据应有可分享、脱敏后的稳定留存和相对链接。监理报告及其证据的补录/链接修正仍由监理负责；开发方列出缺失清单，不擅自搬移或改写。当前有效结论不因首次备份自动失效，但证据的迁移限制必须说明。
- 发现已暂存的敏感文件先移出暂存，不删除用户原件；已推送的凭据立即告知用户并处理凭据失效问题。历史清理需另行明确授权，不能直接强推。

## 6. 分支、同步与回退

- 单人基线不强制每个小步都创建 PR。后续功能可用 `feat/P1-003-...`、修复可用 `fix/P1-002-...`；创建前确认起点及当前修改归属，不为换分支丢弃本地修改。
- 工作区有修改时不盲目拉取、切分支或覆盖；先识别修改并安全保留。不自动 stash 后忘记恢复，也不把别人的修改夹带提交。
- fetch 后先判断分叉。可快进才快进；不能快进时检查具体差异再整合，不为消除冲突删除代码、测试或审查结论。
- 不自动 force push（包括 force-with-lease）、reset --hard、clean -fd、删除远端分支、改写已共享历史。只有用户对具体对象/范围明确授权才能执行。
- 撤回共享提交优先用新的 revert；恢复具体文件前检查未提交修改。Git 能恢复已提交内容，不保证恢复未提交或忽略文件。

## 7. 状态与交接

- STATUS 简述本轮实际操作、分支/同步结果和剩余事项；详细历史由 Git 保存，不在文档复制每条 commit。
- 审查有 Git 后记录被审 commit 和未提交差异；旧 SHA256 证据保留。未提交对象继续用摘要标识，不把旧报告改签成新版本。
- 不将“包含当前 STATUS 的提交自身 SHA”写回该 STATUS 来递归追提交。交付回复报告 commit SHA，文档可引用前序实现 commit、证据文件或既有标签。
- 结束时说明：哪些已本地提交、哪些已推送、实际目标分支/commit、未提交或未跟踪内容、验证状态。认证失败、未推送和暂存内容都要如实交接。
